Both are HTTP 429, `content-type: application/json`, header `retry-after: 60`, body
`{"error":{"message":"Rate limit exceeded for api_key: <hash>. Limit type: <T>. Current limit: <N>, Remaining: 0. Limit resets at: <UTC timestamp>","type":"throttling_error","param":null,"code":"429"}}`

| Case | Limit type | Current limit | Typed error in `gatekeeper/errors.py` | Handled? |
|---|---|---|---|---|
| 3rd and 4th of 4 simultaneous requests | `max_parallel_requests` | 2 | `ConcurrencyLimited`, retry_after 60 | Classified correctly (message contains "parallel"). See finding 2 below |
| Request 21 inside one minute | `requests` | 20 | `QuotaExhausted`, retry_after 60 | Classified correctly. See finding 1 below |

- The quota shape, previously `ASSUMPTION(felcloud)`, is now observed: status 429, `Limit type: requests`, `retry-after: 60`. No shape fell through to `FatalError`.
- The cooldown shape (`all_deployments_in_cooldown`) and 503 did not occur in this run.
- Refused requests answer in 30–280 ms and carry no `x-ratelimit-*` headers (same as recon). `x-ratelimit-api_key-reset-requests` was never present.
- `Limit resets at` is a UTC timestamp in the body; `errors.py` ignores it and uses the header. For the quota case it is about 60 s after the first request of the window; for the concurrency case it is the current second.

## Truncation

Not confirmed. At about 2,500 real prompt tokens the model obeyed an instruction placed at the start and one placed at the end, the server reported the full prompt length in `usage.prompt_tokens`, and no 400 was returned. The middle of the prompt was not probed. `INPUT_TOKEN_BUDGET=1800` is safe, but because the estimator counts 2 chars per token and real French text runs about 3.8 chars per token (3,200 chars = 846 tokens), 1800 estimated tokens is only about 950 real tokens. The belief "FelCloud silently truncates near 2048" was not reproduced.

## `max_tokens` is not enforced

Asked for 10 or 60 tokens with a long-answer prompt, the platform returned 600 to 843 completion tokens with `finish_reason=stop`: compact 600 and 746, mid-size 843 and 816. ## Engine and config changes these results justify (listed, not made)

1. **Quota delay above the retry cap (`MAX_RETRY_WAIT_S=30`).** The real stated delay is 60 s, so `retry.py` raises on the first quota refusal instead of waiting (`delay > max_wait_s` leads to `raise`), and the caller gets `quota_exhausted` with an ETA. The annex says to wait the stated delay. Options: raise `MAX_RETRY_WAIT_S` above 60 (config only), or wait for BACKGROUND and degrade with an ETA for INTERACTIVE.
2. **Concurrency refusal waits the full 60 s.** `ConcurrencyLimited` sleeps `retry-after` (60 s), but the slot is free within a request or two (the body says it resets immediately). Cap that wait at 1 to 2 s. It only matters if another client shares the key, since the local semaphore already holds 2 in flight.
3. **Do not rely on `max_tokens`.** The platform ignores it, so output length, latency and the output-token metric depend on the prompts. Add a length instruction to the explain prompt and a post-hoc cap on `body`; keep the 85 s client timeout under the 90 s server timeout.
4. **Recalibrate the token estimator.** French is about 3.8 chars per token, not 2.0. Measure Arabic and Darija in Arabic script first (they were the slow classify cases), then consider raising `INPUT_TOKEN_BUDGET` for more retrieval context. Keep 1800 until the organizers state the real ceiling.
5. **Convert `ASSUMPTION(felcloud)` comments to `CONFIRMED`** for the quota and concurrency 429 shapes, and add the real bodies to `tests/test_errors.py` as fixtures. Update the "quota-exhausted shape is an assumption" line in `CLAUDE.md`.
6. **Data, not engine:** the tangent-line question produced an ungrounded formula, which points at a gap in `data/docs/` (no tangent-equation section).
